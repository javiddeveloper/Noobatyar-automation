# سیستم اعلان‌ها

هر پیامی که این سیستم به بیرون می‌فرستد از یکی از **چهار کانال** عبور می‌کند.
تفاوتشان در هزینه است، و همین است که تصمیم‌های عجیب‌به‌نظرِ کد را توضیح می‌دهد.

| کانال | گیرنده | هزینه | چه‌کسی می‌فرستد |
|---|---|---|---|
| **FCM** (پوش) | اونر | رایگان | سرور → گوگل → گوشی |
| **پیامک پنل** | مشتری یا اونر | از سهمیه‌ی اشتراک اونر کم می‌شود | سرور → ملی‌پیامک |
| **پیامک دستی** | مشتری | سیم‌کارت خود اونر (خارج از سیستم) | اپ اونر، اپِ پیامک گوشی را باز می‌کند |
| **آلارم محلی** | اونر | رایگان | خودِ گوشی، بدون شبکه |

قانون کلی که همه‌جا رعایت شده: **هیچ‌وقت بی‌سروصدا از سهمیه‌ی اونر خرج نکن.**
هرجا انتخابی بین «رایگان» و «پولی» بوده، پیش‌فرض رایگان است و پولی پشت یک
سوییچ صریح یا یک entitlement پلن قفل شده.

## ۱. نقشه‌ی کامل: چه رویدادی، چه پیامی

### مشتری نوبت می‌گیرد

`appointment/client_views.py` → `_fire_booking_sms` / `_fire_deposit_paid_sms`

| گیرنده | کانال | شرط |
|---|---|---|
| مشتری | پیامک پنل | همیشه (تأیید ثبت نوبت) |
| اونر | **FCM** | همیشه، اگر پوش راه‌اندازی شده باشد |
| اونر | پیامک پنل | فقط اگر `Business.notify_owner_by_sms` روشن باشد — **پیش‌فرض خاموش** |

آن سوییچ پیش‌فرض خاموش است و مایگریشن `business.0013` ردیف‌های موجود را هم
خاموش کرد: اونر نباید از سهمیه‌ی خودش پول بدهد تا چیزی را بشنود که اپش همان
لحظه نشانش می‌دهد. FCM جایگزین همان است.

### اونر نوبت را تأیید یا رد می‌کند

`appointment/views/views.py` → پیامک پنل به مشتری («تأیید شد» / «تأیید نشد»).

### مشتری نوبتش را لغو می‌کند

`appointment/client_views.py` → `_fire_cancellation_sms` → پیامک پنل به اونر،
تا جای خالی‌شده غافلگیرش نکند. به خود مشتری چیزی فرستاده نمی‌شود (`client_msg=None`)
— خودش این کار را کرده، لازم نیست به او خبر داده شود.

### نوبت نزدیک می‌شود ← **اصل ماجرا، بخش ۲**

### کسب‌وکار تأیید/رد/تعلیق می‌شود

`business/sms_moderation.py` → پیامک پنل به شماره‌ای که **اکانت با آن ثبت شده**،
نه `business.phone` (که معمولاً تلفن ثابتِ نمایشی برای مشتری‌هاست).

### اشتراک رو به اتمام است

`accounting/management/commands/run_subscription_lifecycle.py` → پیامک به اونر.
این یکی از سهمیه کم **نمی‌شود** — پیام خودِ پلتفرم درباره‌ی صورت‌حساب است، نه
پیامی که اونر برای کسب‌وکارش می‌فرستد.

### ورود / فراموشی رمز

`api/services/otp.py` → OTP از طریق اندپوینت جدای ملی‌پیامک. خارج از سهمیه.

## ۲. یادآوری نوبت — جایی که همه‌ی پیچیدگی است

یک جاب کرون، **دو کانال کاملاً مستقل**:

```
*/5 * * * *  python manage.py send_appointment_reminders
```

```
                     ┌─────────────────────────────────────┐
   نوبتی که پنجره‌ی   │  send_appointment_reminders         │
   یادآوری‌اش باز شده →│  appointment/management/commands/   │
                     └──────────────┬──────────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
    ┌───────────────────┐                     ┌──────────────────────┐
    │  پوش به اونر      │                     │  پیامک به مشتری      │
    │  _push_owner()    │                     │  _send_one()         │
    │                   │                     │                      │
    │  رایگان           │                     │  از سهمیه کم می‌شود  │
    │  برای همه‌ی        │                     │  فقط اگر:            │
    │  کسب‌وکارهایی که   │                     │   enable_reminder_sms│
    │  notification_    │                     │   AND delivery=PANEL │
    │  enabled دارند    │                     │                      │
    │                   │                     │                      │
    │  مهر:             │                     │  مهر:                │
    │  reminder_push_   │                     │  reminder_sent_at    │
    │  sent_at          │                     │                      │
    └───────────────────┘                     └──────────────────────┘
```

**چرا دو مهر جدا؟** چون دو کانال به دو نفر متفاوت می‌روند و شرط‌هایشان فرق
دارد. با یک مهر مشترک، ارسال موفق پیامک، پوش را خفه می‌کرد و برعکس.

**چرا پوش برای «همه» می‌رود؟** چون رایگان است، و چون کسب‌وکار `MANUAL` — که
پیش‌فرض است — دقیقاً به همین پوش وابسته است: پوش همان تلنگری است که می‌گوید
«برو برای مشتری پیامک بفرست». نسخه‌ی اول این جاب فقط کسب‌وکارهای `PANEL` را
می‌دید، یعنی اونرِ حالت پیش‌فرض هیچ‌وقت خبردار نمی‌شد.

### دو حالت تحویل به مشتری

`Business.reminder_delivery`:

| مقدار | معنی | هزینه | قفل |
|---|---|---|---|
| `MANUAL` (پیش‌فرض) | اونر خودش از سیم‌کارت خودش می‌فرستد | رایگان | ندارد |
| `PANEL` | سرور خودکار می‌فرستد | یک پیامک از سهمیه | نیازمند entitlement `auto_reminder_sms` |

اپ اونر اجازه نمی‌دهد `PANEL` انتخاب شود وقتی پلن پوششش نمی‌دهد، و اگر سرور
با ۴۰۳ جواب داد به `MANUAL` برمی‌گردد
([NotificationsViewModel](../mobile_owner/composeApp/src/commonMain/kotlin/xyz/sattar/javid/proqueue/feature/notifications/NotificationsViewModel.kt)).

### پنجره‌ی زمانی

پنجره در `appointment_date − notification_minutes_before` باز می‌شود و
`MAX_LATENESS` (دو ساعت) بعد بسته می‌شود. آن سقف عمدی است: اگر سرور چند ساعت
پایین بوده، جاب موقع بالا آمدن نباید انبوهی یادآوری بیات شلیک کند.

کوئری روی «پهن‌ترین پنجره‌ی ممکن» فیلتر می‌کند و برش دقیقِ هر کسب‌وکار در
پایتون اعمال می‌شود — چون حساب مدت‌زمان در SQL روی SQLite و PostgreSQL
(هر دو در این پروژه استفاده می‌شوند) یکسان رفتار نمی‌کند.

### پیش‌فرض ۳۰ دقیقه

`DEFAULT_REMINDER_MINUTES = 30` در
[ReminderDefaults.kt](../mobile_owner/composeApp/src/commonMain/kotlin/xyz/sattar/javid/proqueue/domain/model/business/ReminderDefaults.kt)،
هم‌تراز با `Business.notification_minutes_before` در سرور.

قبلاً سه مقدار متناقض وجود داشت (`0` در مدل دامنه، `10` و `20` در
`PreferencesManager`) و فرم ساخت کسب‌وکار اصلاً این فیلد را ست نمی‌کرد — پس هر
کسب‌وکاری که از اپ ساخته می‌شد `notification_minutes_before=0` می‌فرستاد و
یادآوری‌اش سرِ ساعت خودِ نوبت شلیک می‌شد. کسب‌وکارهایی که هنوز `0` ذخیره دارند
موقع لود، پیش‌فرض را نشان می‌دهند.

## ۳. FCM — از سرور تا گوشی

جهت یک‌طرفه است. **سرور هیچ‌وقت از FCM چیزی دریافت نمی‌کند:**

```
اپ اونر                    سرور جنگو                  گوگل/FCM         گوشی
   │                          │                          │              │
   │  ثبت توکن دستگاه          │                          │              │
   ├─────────────────────────►│                          │              │
   │  POST /api/devices/      │  DeviceToken             │              │
   │       register/          │  (api/models.py)         │              │
   │                          │                          │              │
   │                          │  push.send_to_user()     │              │
   │                          ├─────────────────────────►│              │
   │                          │  HTTP v1 + service acct  ├─────────────►│
   │                          │                          │   نوتیفیکیشن  │
```

### احراز هویت: service account، نه server key

گوگل server keyهای قدیمی (`/fcm/send`) را بسته. `api/services/push.py` با
HTTP v1 کار می‌کند: یک کلید خصوصی service account که `google-auth` از رویش
توکن OAuth کوتاه‌عمر می‌سازد. راه‌اندازی‌اش در [FCM_SETUP.md](FCM_SETUP.md).

### همه‌جا نرم شکست می‌خورد

پوش کانال **کنارِ** پیامکی است که پیام واقعی را می‌برد. پس نبودِ فایل کلید،
یا قطعی FCM، هرگز نباید اجرای یادآوری را بترکاند. `is_configured()` بدون
استثنا `False` برمی‌گرداند و جاب بدون خطا ادامه می‌دهد.

### چرخه‌ی عمر توکن دستگاه

| کِی | چه اتفاقی می‌افتد |
|---|---|
| هر استارتِ لاگین‌شده‌ی اپ | `SyncPushTokenUseCase` توکن فعلی را دوباره ثبت می‌کند |
| FCM توکن را چرخاند | `PushMessagingService.onNewToken` → ثبت مجدد |
| لاگ‌اوت | `UnregisterPushTokenUseCase` → `is_active=False` |
| FCM گفت `UNREGISTERED` | `send_to_user` خودش ردیف را غیرفعال می‌کند |

`DeviceToken.token` در کل جدول یکتاست، نه به‌ازای هر کاربر. عمدی است: FCM به
هر **نصب** یک توکن می‌دهد، پس وقتی اکانت دومی روی همان گوشی وارد می‌شود ردیف
باید **جابه‌جا** شود، وگرنه اونر قبلی همچنان اعلان نوبت‌های کسی دیگر را
می‌گیرد.

ثبتِ خودکار در هر استارت (نه فقط بعد از لاگین) عمدی است: FCM توکن‌ها را با
برنامه‌ی خودش می‌چرخاند (نصب مجدد، ریستور بکاپ، پاک‌کردن دیتای اپ) و توکن بیات
بی‌سروصدا غیرقابل‌تحویل است. دوباره‌فرستادنِ توکن فعلی ارزان‌تر از تشخیص چرخش است.

## ۴. کانال نوتیفیکیشن اندروید — تله‌ای که یک‌بار خوردیم

**هر سه نوعِ اعلانِ اونر روی یک کانال می‌نشینند:** `appointment_reminders`.
تا اونر در تنظیمات سیستم یک سوییچ داشته باشد، نه سه‌تا که تقریباً یک معنی دارند.

این شناسه در **سه جا** باید یکی باشد و
[NotificationChannels.kt](../mobile_owner/composeApp/src/androidMain/kotlin/xyz/sattar/javid/proqueue/core/notifications/NotificationChannels.kt)
مالک آن است:

1. `NotificationChannels.APPOINTMENT_REMINDERS`
2. `default_notification_channel_id` در `AndroidManifest.xml`
3. `settings.FCM_ANDROID_CHANNEL_ID` در سرور

> ⚠️ **کانال باید در `ProQueueApp.onCreate` ساخته شود، نه موقع نمایش اولین
> نوتیفیکیشن.**
>
> وقتی اپ در پس‌زمینه است، نوتیفیکیشن را **خودِ SDK فایربیس** پست می‌کند با
> همان `default_notification_channel_id` منیفست — کد ما اصلاً اجرا نمی‌شود. و
> اندروید نوتیفیکیشنی که کانالش وجود ندارد را بی‌صدا دور می‌ریزد: بدون خطا،
> بدون لاگ، بدون هیچ ردی در `dumpsys`.
>
> در نسخه‌ی اول، کانال فقط داخل `showNotification()` ساخته می‌شد. نتیجه: روی
> **هر نصب تازه**، تمام پوش‌ها ناپدید می‌شدند تا وقتی تصادفاً یک آلارم محلی
> اول کانال را بسازد. FCM دویست برمی‌گرداند، سوکت وصل بود، پرمیشن گرنت بود، و
> هیچ‌چیز نمی‌آمد. تست‌های اولیه نگرفتندش چون `adb install -r` روی نصب قدیمی
> بود و دیتای اپ کانال را از قبل داشت.

### دو مسیر نمایش

| اپ کجاست | چه‌کسی نوتیفیکیشن را می‌سازد |
|---|---|
| پس‌زمینه / بسته | SDK فایربیس، از بلوک `notification` پیام |
| پیش‌زمینه | `PushMessagingService.onMessageReceived` |

به همین دلیل پیام هم `notification` دارد و هم `data`: بدون بلوک `notification`
حالت پس‌زمینه چیزی نشان نمی‌دهد، و بدون `onMessageReceived` اپِ باز ساکت
می‌ماند. `data` هم شناسه‌ها را می‌برد تا تپ‌کردن روی اعلان به جای درست ببرد.

## ۵. آلارم محلی — کانال چهارم

مستقل از FCM و مستقل از سرور. موقع ساخت نوبت در اپ،
[CreateAppointmentUseCase](../mobile_owner/composeApp/src/commonMain/kotlin/xyz/sattar/javid/proqueue/domain/usecase/CreateAppointmentUseCase.kt)
یک آلارم روی خود گوشی می‌گذارد:

- **اندروید:** `AlarmManager.setExactAndAllowWhileIdle` → `ReminderReceiver`.
  روی اندروید ۱۲+ اگر `canScheduleExactAlarms()` نباشد به نسخه‌ی غیردقیق
  برمی‌گردد (دیر می‌رسد، ولی می‌رسد).
- **iOS:** `UNTimeIntervalNotificationTrigger`.

این کانال تنها چیزی است که روی **iOS** کار می‌کند — آنجا FCM عمداً غیرفعال
است (بخش ۷).

نکته‌ی مهم: آلارم محلی فقط برای نوبت‌هایی است که **در همان اپ ساخته شده‌اند**.
نوبتی که مشتری از وب گرفته آلارمی روی گوشی اونر ندارد؛ آن یکی از مسیر FCM
می‌آید. برای همین هر دو کانال لازم‌اند.

## ۶. پیامک دستی — چطور اونر خودش می‌فرستد

حالت `MANUAL` هیچ پیامکی از سرور نمی‌فرستد. به‌جایش:

1. اونر پوش یادآوری می‌گیرد («یادآوری را برای مشتری بفرستید»).
2. در اپ، `GenerateReminderMessageUseCase` متن را از قالب اونر می‌سازد.
3. `openSms(phone, message)` اپِ پیامک خود گوشی را با متن آماده باز می‌کند.
4. اونر دکمه‌ی ارسال را می‌زند — پیامک از سیم‌کارت خودش می‌رود.

قالب پیام و توکن‌هایش (`{visitor}`, `{business}`, `{time}`, `{minutes}`,
`{duration}`, `{date}`, `{address}`) در صفحه‌ی «پیام‌ها» قابل ویرایش است و در
`PreferencesManager` به‌ازای هر کسب‌وکار ذخیره می‌شود — نه روی سرور.

`{minutes}` همان `notification_minutes_before` است؛ صفحه‌ی اعلان‌ها موقع ذخیره
آن را در `PreferencesManager` هم می‌نویسد تا این دو از هم جدا نیفتند.

## ۷. iOS

پوش ندارد و عمدی است. `PushTokenProvider.ios.kt` مقدار `null` برمی‌گرداند، پس
هیچ دستگاهی ثبت نمی‌شود و بقیه‌ی مسیر مشترک بدون تغییر کامپایل می‌شود.

FCM روی iOS سوار APNs است و به یک APNs Auth Key از Apple Developer، انتیتلمنت
`aps-environment`، و لینک‌شدن SDK آی‌اواس فایربیس در پروژه‌ی Xcode نیاز دارد —
هیچ‌کدام هنوز وجود ندارد. تا آن موقع اپ iOS یادآوری‌ها را فقط از آلارم محلی
(بخش ۵) می‌گیرد.

## ۸. سهمیه و حسابداری پیامک

هر پیامکی که به حساب اونر نوشته می‌شود از این مسیر رد می‌شود:

```python
receipt = usage.consume_sms(owner_id)
if not receipt:
    SmsLog.objects.create(..., status='SKIPPED_QUOTA')
    return                       # اعتبار تمام است — نفرست

ok, err = send_sms(phone, message)
if not ok:
    usage.refund_sms(receipt)    # ارائه‌دهنده قبول نکرد → پول برگردد

SmsLog.objects.create(..., status='SENT' if ok else 'FAILED')
```

سه قاعده که هیچ‌جا نباید شکسته شوند:

1. **اول کسر، بعد ارسال.** اگر اعتبار نیست، اصلاً نفرست.
2. **ارسال ناموفق قابل صورت‌حساب نیست** — `refund_sms` حتماً صدا زده شود.
3. **همه‌چیز در `SmsLog` ثبت شود**، حتی `SKIPPED_QUOTA` و حتی پیام‌هایی که به
   خودِ اونر می‌روند (`visitor=None`). این لاگ چیزی است که به سؤال «چرا
   اعتبار پیامکم تموم شد؟» جواب می‌دهد و باید با سهمیه‌ی کسرشده بخواند.

یک استثنا: پیامک یادآوری تمدید اشتراک از سهمیه کم نمی‌شود — پیام پلتفرم است.

### قواعد خط تبلیغاتی ملی‌پیامک

`api/sms.py` سه محدودیت را در مرز ارسال اعمال می‌کند، چون خط تبلیغاتی است:

- هر پیام باید به `لغو11` ختم شود
- لینک ممنوع — و فیلترشان **نقطه** را هم لینک می‌شمارد، پس نقطه‌ها حذف می‌شوند
- تحویل فقط بین ۸ صبح تا ۱۰ شب

بیرونِ آن بازه، خط پیام را قبول می‌کند و `recId` معتبر می‌دهد ولی هرگز تحویل
نمی‌دهد. برای همین `send_sms` خودش امتناع می‌کند و `False` برمی‌گرداند — تا
`SmsLog` دروغ نگوید و اعتبار برگردد.

`signed()` تنها جایی است که این قواعد اعمال می‌شود؛ هر پیام خروجی باید از آن
رد شود.

## ۹. تنظیمات — چه چیزی کجا زندگی می‌کند

| تنظیم | کجا ذخیره می‌شود | چه‌کسی می‌خواندش |
|---|---|---|
| `notification_enabled` | سرور (`Business`) | جاب یادآوری |
| `notification_minutes_before` | سرور (`Business`) | جاب یادآوری + آلارم محلی |
| `enable_reminder_sms` | سرور (`Business`) | جاب یادآوری |
| `reminder_delivery` | سرور (`Business`) | جاب یادآوری |
| `notify_owner_by_sms` | سرور (`Business`) | مسیر رزرو |
| قالب پیام | فقط لوکالِ اپ (`PreferencesManager`) | پیامک دستی |
| `notificationReminderMinutes` | لوکالِ اپ، آینه‌ی مقدار سرور | توکن `{minutes}` قالب |

هرچه روی رفتار **سرور** اثر دارد روی سرور است. تنها چیز واقعاً لوکال، قالب
پیام است — چون فقط اپ خودش آن را برای باز کردن اپِ پیامک لازم دارد.

صفحه‌ی «اعلان‌ها» در اپ اونر چهار فیلد اول را می‌نویسد. قبل از این، آن صفحه
هیچ راهی به مشتری نداشت: `enable_reminder_sms` و `reminder_delivery` فقط در
دیتابیس بودند و از اپ دست‌نیافتنی، پس همه‌ی کسب‌وکارها روی پیش‌فرضشان
می‌ماندند.

## ۱۰. عیب‌یابی

### پوش نمی‌رسد

به ترتیب چک کن — هر کدام یک حلقه‌ی متفاوت است:

```bash
# ۱. سرور اصلاً پیکربندی شده؟
python manage.py shell -c "from api.services import push; print(push.is_configured())"

# ۲. دستگاهی ثبت شده؟
python manage.py shell -c "from api.models import DeviceToken; print(list(DeviceToken.objects.values('user__phone','platform','is_active')))"

# ۳. ارسال مستقیم
python manage.py shell -c "from api.services import push; print(push.send_to_user(<USER_ID>,'تست','سلام'))"
```

اگر `send_to_user` عددی بزرگ‌تر از صفر داد ولی گوشی چیزی نشان نداد، مشکل
سمت دستگاه است:

```bash
# کانال اصلاً وجود دارد؟  ← شایع‌ترین علت، بخش ۴ را ببین
adb shell dumpsys notification | grep -A3 "AppSettings: xyz.sattar.javid.proqueue" | grep mId

# نوتیفیکیشن پست شده؟  tag=FCM-Notification: یعنی مسیر پس‌زمینه
adb shell dumpsys notification --noredact | grep "pkg=xyz.sattar.javid.proqueue"

# پرمیشن
adb shell dumpsys package xyz.sattar.javid.proqueue | grep POST_NOTIFICATIONS

# سوکت تحویل FCM وصل است؟ (146C = پورت 5228)
adb shell 'cat /proc/net/tcp /proc/net/tcp6' | grep -c ":146C "
```

**۲۰۰ گرفتن از FCM یعنی «گوگل قبول کرد»، نه «گوشی نشان داد».** بین این دو،
کانال و پرمیشن قرار دارند.

### یادآوری نمی‌رود

```bash
python manage.py send_appointment_reminders --dry-run
```

هر نوبت با `sms=yes/no push=yes/no` چاپ می‌شود. اگر نوبتی اصلاً در لیست نیست:

- `notification_enabled` کسب‌وکار خاموش است؟
- وضعیت نوبت در `('WAITING','CONFIRMED')` هست؟
- پنجره باز شده؟ (`appointment_date − minutes_before` باید بین «الان منهای دو
  ساعت» و «الان» باشد)
- قبلاً مهر خورده؟ `reminder_sent_at` / `reminder_push_sent_at`

اگر `sms=no` است ولی انتظار پیامک داری: `reminder_delivery` روی `PANEL` است؟
`enable_reminder_sms` روشن است؟

### پیامک نمی‌رود

- `SmsLog` را ببین: `SKIPPED_QUOTA` یعنی اعتبار تمام، `FAILED` یعنی
  `error_detail` را بخوان.
- ساعت را چک کن — بیرون بازه‌ی ۸ تا ۲۲ عمداً رد می‌شود.
- `MELIPAYAMAK_OTP_TOKEN` و `MELIPAYAMAK_FROM` ست هستند؟

## ۱۲. اگر می‌خواهی چیزی اضافه کنی

**یک اعلان جدید به اونر:** `push.send_to_user()` را صدا بزن. رایگان است، پس
لازم نیست پشت سوییچی قفلش کنی. حتماً داخل `try/except` که مسیر اصلی را
نشکند، و `is_configured()` را اول چک کن.

**یک پیامک جدید:** متن را با `signed()` بساز (وگرنه بدون `لغو11` می‌رود و رد
می‌شود)، از `consume_sms`/`refund_sms` رد شو، و در `SmsLog` بنویس. اگر پیام
پلتفرمی است (نه پیامی که اونر برای کسب‌وکارش می‌فرستد)، از سهمیه کم نکن و
دلیلش را کامنت بگذار.

**یک کانال اندرویدی جدید:** لازم نداری. مگر اینکه واقعاً بخواهی اونر بتواند
جداگانه خاموشش کند — که آن‌وقت باید در `NotificationChannels` ساخته شود، در
`onCreate`، وگرنه دقیقاً به همان تله‌ی بخش ۴ می‌خوری.
